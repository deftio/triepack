# Release procedure

## Branch model

`main` is the production branch. All work happens on feature branches named
`feature/<short-description>` or `fix/<short-description>`. Only the maintainer
merges to `main`, and only by squash-merge after CI is green. Direct commits to
`main` are not part of the process, including version bumps — those go through
the release PR like anything else.

## Versioning

`triepack-version.txt` at the repository root is the single source of truth.
One line, `X.Y.Z`, nothing else.

Everything else derives from it:

| Consumer | How |
|---|---|
| `CMakeLists.txt` | reads the file directly |
| `triepack_version.h` (`TP_VERSION_STRING`) | generated by CMake |
| `trp` CLI (`trp version`) | prints `TP_VERSION_STRING` |
| npm, PyPI, Cargo, Gradle manifests | `scripts/sync_version.sh` |
| Kotlin `VERSION`, Python `__version__` | `scripts/sync_version.sh` |
| docs site header, README title | `scripts/sync_version.sh` |

```bash
./scripts/sync_version.sh           # propagate
./scripts/sync_version.sh --check   # verify; exits 1 on drift
```

CI runs `--check` on every push and pull request, so a manifest cannot drift
from the version file without a red build.

The on-disk **format** version (`TP_VERSION_MAJOR` / `TP_VERSION_MINOR` in the
encoders) is deliberately *not* synced. It describes the bytes in a `.trp`
file and moves only when the format changes.

## Cutting a release

```bash
./scripts/make-release.sh --check          # gate only, run this any time
./scripts/make-release.sh --version 1.2.0  # the real thing
```

`make-release.sh` does, in order:

1. **Preflight** — clean working tree, `git` and `gh` present and
   authenticated.
2. **Version** — writes `triepack-version.txt` and runs `sync_version.sh`.
3. **Build and test every target** — C/C++ (zero-warning build plus `ctest`),
   the conformance corpus regeneration check, then JavaScript, TypeScript,
   Python, Go, Rust, Swift, Java and Kotlin. A missing toolchain is a failure,
   not a silent skip; pass `--skip go,rust` to release without a target you
   genuinely cannot run, and the summary will say so.
4. **Release branch and PR** — commits the bump on `release/vX.Y.Z`, pushes,
   opens the PR.
5. **Waits for CI** — `gh pr checks --watch --fail-fast`.
6. **Squash-merges**, then tags `vX.Y.Z` on `main` and pushes the tag.

It prompts before each irreversible step. `--yes` skips the prompts and
`--dry-run` prints the git and gh commands instead of running them.

## What the tag triggers

Pushing `vX.Y.Z` runs `.github/workflows/release.yml`:

1. **version** — the tag must equal `triepack-version.txt`, and
   `sync_version.sh --check` must pass.
2. **test-c** and **test-bindings** — the whole matrix again, on clean
   runners.
3. **github-release** and **npm** — both `needs:` every job above, so nothing
   is published unless all of it is green.

The npm job is idempotent: if that version is already on the registry it logs
and exits rather than failing the run.

## npm publishing

The published package is `triepack`, built from `bindings/javascript`. It
ships the sources, the bundled TypeScript declarations
(`src/index.d.ts`), the README and the licence — 11 files, no tests, no
fixtures.

`bindings/typescript` is an in-repo wrapper marked `"private": true`. It used
to claim the same npm name and required the JavaScript binding by a relative
path that does not exist in a published tarball, so it is not publishable;
TypeScript users get types from the main package.

### Trusted publishing (OIDC)

The workflow already requests `id-token: write` and publishes with
`--provenance`, which is everything needed on the CI side. To switch off
tokens entirely:

1. On npmjs.com, open the `triepack` package → Settings → Trusted publisher.
2. Add GitHub Actions with repository `deftio/triepack` and workflow
   `release.yml`.
3. Delete the `NPM_TOKEN` repository secret.

Until a trusted publisher is configured, the job authenticates with the
`NPM_TOKEN` secret (an npm automation token). Both paths use the same step;
`NODE_AUTH_TOKEN` is simply ignored once OIDC is in place.

### First publish

The name is unregistered, so the first publish also claims it. Check the
tarball first:

```bash
cd bindings/javascript && npm pack --dry-run
```

## PyPI

`bindings/python` carries complete PyPI metadata — SPDX licence expression,
classifiers, project URLs, README — and builds a clean wheel and sdist that
pass `twine check`:

```bash
cd bindings/python
python -m build
twine check dist/*
```

No publish workflow is wired up yet. Adding one means a job alongside `npm` in
`release.yml` with `id-token: write`, using PyPI's trusted publishing.

## Checklist

- [ ] `CHANGELOG.md` has an entry for the version
- [ ] `./scripts/make-release.sh --check` is green on every target
- [ ] `triepack-version.txt` holds the new version
- [ ] `./scripts/make-release.sh --version X.Y.Z`
- [ ] GitHub Release looks right
- [ ] `npm view triepack version` matches
- [ ] Docs site shows the new version in the header
